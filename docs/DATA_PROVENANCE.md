## How the distinction is maintained

The extraction and pipeline commands require `--provenance generated` or `--provenance personal`. The label and source hash are written to task JSON, carried into simulation results, and shown in tracking/rollout overlays. The label is supplied by the person running the command; it is not an automated detector of generated content.

For every real recording, retain the original file and note the date, measured marker-to-marker workspace size, object dimensions, layout, and outcome. If thresholds or simulator geometry are adjusted after inspecting a clip, record it as development data. Evaluation recordings should be identified before testing and should remain separate from tuning clips.

Real and generated results should be presented separately. The challenge requires data personally collected by the applicant; the generated prototype alone does not meet that condition.

## Using different real objects

Yes, the next stage can use other real objects. The scope of the change matters:

- **Red and blue small boxes, including boxes wrapped in colored tape:** closest to the current system. Check dimensions and calibration; adjust the simulated cuboids if they differ from 4 cm cubes.
- **Cans or other cylinders:** require matching collision geometry and a suitable grasp. The existing cube result does not establish that the same controller will succeed.
- **Objects without distinct red/blue appearance:** require a new identification/segmentation method or explicit visual markers. The current extractor has only two color identities.
- **Transparent, reflective, deformable, or irregular objects:** introduce additional perception and contact-model problems. They are a larger extension than changing the object layout.

For the first personally recorded run, use rigid, easily distinguished objects and keep the tabletop markers and matching target rings. Record what the objects actually are; if the simulation approximates them as simpler shapes, state that approximation. The robot need not reproduce the human hand shape, but the experiment must clearly show which aspects of the task came from the applicant's footage.

## Evidence to publish with the final challenge repository

- At least one applicant-recorded example, or an accessible link, with the corresponding extracted task and outputs.
- A short account of collection conditions and any preprocessing or manual annotations.
- Separate development and evaluation records, including failures and changes prompted by them.
- Run commands and dependency/model versions, plus explicit current limitations.
- A clearly labeled Gemini prototype example if it is included in the project history.

The `.gitignore` excludes raw personal videos and generated output folders. Explicit exceptions allow the labeled Gemini input and the prototype comparison in `examples/media/` and `docs/media/`. Selected real-data submission artifacts will be added deliberately when that stage is ready.
